# WabiDB Storage Manifest Specification

> **Card:** wabidb-10 (Phase 1, Storage Manifest)
> **Status:** v1 specification
> **Source of truth:** `docs/proposals/wabidb-endstate.md` §11.5 (Manifest-Based Backup, P0-6 Fix) and §12 (Operations)
> **Companion to:** `core/crates/wabidb/docs/STORAGE_FORMAT.md` (which covers segment/commit-index/blob formats)
> **Date:** 2026-06-20

This document specifies the **storage manifest** — the canonical artifact produced by `wabidb backup` (wabidb-68) and verified by `wabidb verify-backup` (wabidb-69). The manifest is the contract that allows a backup to be moved to a different host and restored (wabidb-87 / wabidb-93) without losing data.

## 1. Why a manifest

A backup of `$DATA_DIR/` is not just a directory copy. The directory has:

- Stream segments that may be sealed (no more appends) or current (still being appended)
- A commit index with sealed files and one current file
- Blob files referenced by events in the segments
- An optional `storage-manifest.json` describing the layout

Without a manifest, a backup has no way to know:

- Which files are sealed vs. still being written
- The `highest_commit_seq` at the time of backup
- Whether all files are present and uncorrupted
- What streams exist and their last-known state

The manifest answers all of these. It is generated by the backup procedure and frozen — the backup procedure never modifies a sealed manifest. Verification reads the manifest and checks every file referenced by it.

## 2. File location and naming

The manifest is stored at:

```
$DATA_DIR/manifests/storage-manifest.json
```

There is **exactly one** manifest per data directory. The backup procedure copies this file (along with the rest of the data directory) to the backup target. Restoration reads the manifest from the backup target.

The file is named `storage-manifest.json` to avoid collision with backup-specific metadata files that the backup procedure may produce (e.g., `backup-2026-06-20.json` for audit logs).

## 4. Field reference

### 4.1 Top-level fields

| Field | Type | Required | Description |
|---|---|---|---|
| `$schema` | string | recommended | URI of the JSON Schema. Used by validation tools. |
| `schema_version` | integer | yes | Schema version. Current: `1`. |
| `format_version` | integer | yes | On-disk format version of the data files. Matches the engine's expected format. |
| `engine_version` | string | yes | Engine version that produced the manifest. |
| `backup_id` | ULID string | yes | Unique identifier for this backup. |
| `created_at_micros` | integer | yes | Server time when the backup was created, in microseconds since epoch. |
| `data_dir` | string | yes | Absolute path of the data directory that was backed up. |
| `highest_commit_seq` | integer | yes | The `commit_seq` of the most recent commit at backup time. |
| `highest_sealed_commit_index` | integer | yes | The number of sealed commit-index files at backup time. |
| `current_commit_index` | integer | yes | The number of the current (still-being-appended) commit-index file. |
| `config` | object | yes | Engine configuration at backup time. See §4.2. |
| `streams` | array | yes | One entry per stream. See §4.3. |
| `commit_index_files` | array | yes | One entry per commit-index file. See §4.4. |
| `blobs` | array | yes | One entry per blob. See §4.5. |
| `totals` | object | yes | Aggregate counts. See §4.6. |
| `verification` | object | optional | Populated by `wabidb verify-backup`. See §4.7. |

### 4.2 `config` object

The engine configuration that was active at backup time. This is informational; restoration does not re-apply the config. Restoration writes its own config (the engine that restores knows its own config).

| Field | Type | Description |
|---|---|---|
| `segment_size_bytes` | integer | Segment rotation threshold. Default: 67108864 (64 MiB). |
| `commit_batch_size` | integer | Commit-index batch size. Default: 10. |
| `commit_batch_age_micros` | integer | Commit-index batch age. Default: 50000 (50 ms). |
| `backpressure_timeout_micros` | integer | Subscription backpressure timeout. Default: 5000000 (5 s). |
| `reaper_interval_micros` | integer | Retention reaper interval. Default: 60000000 (60 s). |
| `snapshot_threshold_events` | integer | Snapshot frequency. Default: 10000 events. |
| `snapshot_threshold_age_micros` | integer | Snapshot age. Default: 86400000000 (24 h). |
| `load_shed_backlog_threshold` | integer | Commit backlog that triggers degraded mode. Default: 50000. |
| `max_record_payload_bytes` | integer | Maximum record payload size. Default: 16777216 (16 MiB). |
| `record_alignment_bytes` | integer | Record padding alignment. Default: 16. |

### 4.3 `streams` array

One entry per stream that exists in the data directory. Each entry describes the stream's identity, key range, segments, and snapshots.

| Field | Type | Description |
|---|---|---|
| `stream_id` | string | The stream's ID (e.g. `"ch_01H..."`). |
| `stream_kind` | integer | 1=channel, 2=dm, 3=whiteboard, 4=place, 5=kanban, 6=other. |
| `stream_key_id` | ULID string | The ID of the active encryption key for this stream. |
| `key_min_commit_seq` | integer | The active key's minimum allowed `commit_seq`. |
| `key_max_commit_seq` | integer | The active key's maximum allowed `commit_seq` (per Council Review #1 §1.1). |
| `segment_files` | array of strings | The segment file names (relative to the stream's `events/` directory). Ordered by segment number. |
| `segment_count` | integer | The number of segment files. |
| `total_record_count` | integer | The total number of records across all segments. |
| `total_size_bytes` | integer | The total size of all segment files in bytes. |
| `created_at_micros` | integer | When the stream was first created. |
| `last_commit_seq` | integer | The `commit_seq` of the most recent record in this stream. |
| `snapshot_files` | array of strings | The snapshot file names. Ordered by snapshot number. |

### 4.4 `commit_index_files` array

One entry per commit-index file. The most recent file has `sealed: false`; older files are sealed.

| Field | Type | Description |
|---|---|---|
| `path` | string | The file's path relative to `$DATA_DIR`. |
| `sealed` | boolean | `true` if the file is sealed (no more appends); `false` if it is the current file. |
| `entry_count` | integer | The number of `CommitIndexEntry` records in this file. |
| `first_commit_seq` | integer | The `commit_seq` of the first entry. |
| `last_commit_seq` | integer | The `commit_seq` of the last entry. |
| `size_bytes` | integer | The file size in bytes. |
| `sha256` | string | Hex-encoded SHA-256 of the file contents (for verification). |

### 4.5 `blobs` array

One entry per blob. Empty if the data directory has no blobs.

| Field | Type | Description |
|---|---|---|
| `hash` | string | BLAKE3 hash of the blob (the content-addressed identifier). |
| `path` | string | The blob data file path relative to `$DATA_DIR`. |
| `meta_path` | string | The blob metadata file path. |
| `size_bytes` | integer | The size of the blob data file. |
| `ref_count` | integer | The number of references to this blob (from events, etc.). Used for GC. |

### 4.6 `totals` object

Aggregate counts for verification. The `verify-backup` command re-computes these and compares them to the manifest.

| Field | Type | Description |
|---|---|---|
| `stream_count` | integer | The number of streams. |
| `segment_count` | integer | The total number of segment files across all streams. |
| `commit_index_file_count` | integer | The number of commit-index files. |
| `blob_count` | integer | The number of blobs. |
| `total_data_bytes` | integer | The sum of all file sizes in bytes. |

### 4.7 `verification` object

Populated by `wabidb verify-backup` (wabidb-69). Optional in the manifest produced by `wabidb backup`; required after a verification pass.

| Field | Type | Description |
|---|---|---|
| `verified_at_micros` | integer | When the verification was performed. |
| `verified_by` | string | The tool that verified (e.g., `"wabidb verify-backup 0.1.0"`). |
| `all_files_present` | boolean | `true` if every file referenced by the manifest exists. |
| `all_checksums_matched` | boolean | `true` if every file's SHA-256 matches. |
| `errors` | array of strings | Human-readable error messages. Empty if verification passed. |

## 5. Production procedure (`wabidb backup`)

1. Acquire a read lock on the commit sequencer (wabidb-15). New commits are blocked; in-flight commits drain.
2. Read the current `highest_commit_seq`.
3. Walk the data directory and collect:
   - All segment files in each stream's `events/` directory
   - All snapshot files in each stream's `snapshots/` directory
   - All commit-index files in `global/commit-index/`
   - All blob files in `blobs/`
4. For each file, compute the SHA-256.
5. Walk the in-memory projection state to enumerate streams and their metadata.
6. Compose the manifest JSON.
7. Atomically write the manifest to `$DATA_DIR/manifests/storage-manifest.json` (write to temp, fsync, rename, fsync dir).
8. Release the commit sequencer lock.
9. Copy the data directory (including the manifest) to the backup target.

The read lock in step 1 is the moment of consistency. The manifest is internally consistent at that instant. A backup taken at instant T contains all commits with `commit_seq <= highest_commit_seq_at_T`.

## 6. Verification procedure (`wabidb verify-backup`)

Given a backup directory containing a `manifests/storage-manifest.json`:

1. Read the manifest.
2. For each file referenced by the manifest:
   a. Check that the file exists.
   b. Compute the SHA-256 of the file and compare to the manifest's `sha256`.
3. Re-compute the `totals` and compare to the manifest's `totals`.
4. Populate the `verification` object.
5. If any file is missing or any checksum mismatches, exit non-zero with a human-readable error.
6. Otherwise, exit zero with a "OK: all files match" message.

## 7. Restoration procedure (`wabidb restore`)

1. Verify the backup first (`wabidb verify-backup` must pass). Refuse to restore a broken backup.
2. Check that the target directory is empty (or that the user has confirmed overwriting).
3. Copy all files from the backup directory to the target.
4. Read the manifest to confirm the highest `commit_seq` matches what the engine expects.
5. The engine starts, scans the commit index, and rebuilds projections. The manifest is informational; the engine doesn't read it on startup.

## 8. What the manifest is NOT

- **Not a source of truth.** The source of truth is the commit index (per Council Review #1 §2.2). The manifest is a backup artifact, not a runtime data structure.
- **Not authoritative for configuration.** The manifest records the config that was active at backup time. Restoration does not re-apply it; the engine that restores knows its own config.
- **Not a journal.** The manifest is a point-in-time snapshot. It is not updated incrementally as the data directory changes. A new backup produces a new manifest.

## 9. Versioning

The manifest has a `schema_version`. A reader that doesn't recognize the `schema_version` must reject the manifest (not panic). The current version is `1`.

Adding new fields to the manifest is a **minor version bump** (1 → 2). Removing a field is a **major version bump** (1 → 3). Renaming a field is a **major version bump**.

Old readers can ignore unknown fields. Old readers MUST be able to read a newer-schema manifest with required fields it doesn't recognize; it should reject the manifest, not partially process it.
