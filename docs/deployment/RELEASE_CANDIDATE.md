# Release Candidate Workflow

## Overview

This document describes the Wabi release candidate generation process. Candidates are **draft, prerelease** artifacts that require real physical acceptance testing before any publication.

## Build Identity

The canonical builds receive `WABI_SOURCE_REVISION` — the full Git SHA of the exact checkout through `WABI_SOURCE_REVISION`. The server manifest and rendered About page identify the embedded client/server; native installers are packaged from the corresponding CI job and covered by the asset checksums. The identity manifest (`wabi-release-manifest.json`) records:

- **Server**: component name, version, source revision, build profile, OS/architecture, binary SHA-256 and size
- **Client**: frontend build revision, tree SHA-256, file count, and per-file hashes
- **Source revision** matching between server and client is asserted

The manifest is generated by `scripts/write-release-manifest.mjs` and must be present alongside every server binary.

## How to Download and Verify Artifacts

### Download artifacts from a release

```bash
# List available assets
gh release view TAG --repo OWNER/REPO --json assets

# Download specific asset
gh release download TAG --repo OWNER/REPO --dir candidate
cd candidate
```

### Verify checksums

```bash
# SHA256SUMS is generated from all dist basenames
sha256sum -c SHA256SUMS
```

### Extract the server .tar.gz

```bash
tar -xzf wabi-server-linux-x86_64.tar.gz
# Contains: wabi-server (executable) and wabi-release-manifest.json
```

### Inspect the build identity

```bash
./wabi-server --build-info
cat wabi-release-manifest.json
```

## Draft Review Gate

All GitHub releases created by the workflow are:

- `--draft` — not visible to the public until a maintainer publishes them
- `--prerelease` — marked as prerelease, not stable
- `--title "Wabi TAG"` — uses the tag name as the release title

**No stable release is ever published automatically.** Every release must pass through manual review.

The release job will **fail if a release with the same tag already exists**, preventing accidental overwrites of published assets.

## Platform Status

| Platform | Status | Notes |
|----------|--------|-------|
| Linux (.deb, .rpm, AppImage) | First pilot — **not yet certified** | Configured installer outputs; CI execution still needs acceptance |
| Windows (.msi, NSIS .exe) | First pilot — **not yet certified** | Configured installer outputs; CI execution still needs acceptance |
| macOS (.dmg, universal) | Existing builds — **unvalidated** | Universal Apple target remains configured |

**No actual release has been created.** All generated artifacts are draft candidates requiring physical acceptance testing.

## The Old Manual Workflow

The previous `.github/workflows/tauri-build.yml` included an automatic `create-release` job that could not be triggered (no tags trigger that workflow) and duplicated the native build pipeline. It has been **removed**. That workflow now runs only as `workflow_dispatch` for manual native diagnostic builds and does **not** publish any releases.

## Packaging checks

`scripts/package-release-candidate.mjs` consumes the already-built server and desktop artifacts. It verifies the server byte hash, size and client/server source revisions, refuses duplicate installer basenames, preserves executable mode in the server archive, and produces one checksum list for every downloadable asset. It does not rebuild the server in a separate release job. All three configured desktop jobs must complete for this draft workflow; Apple hardware acceptance remains outside the first pilot target.

An existing release or output directory is not overwritten. Signing, platform installation/upgrade tests and actual tagged CI execution remain separate release gates. Build identity is traceability, not signing or platform certification.

Workflow behavior follows [GitHub tag trigger rules](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) and [Tauri installer targets](https://v2.tauri.app/distribute/windows-installer/).

## Never Publish Stable Automatically

The release workflow only creates `--draft --prerelease` candidates. Stable publication requires explicit manual action by a maintainer after acceptance testing.
