# Shared Wabi Media Node Setup

**Status:** early implementation / operator testing  
**Updated:** 2026-09-14

A shared Wabi Media Node lets one publicly reachable SFU serve several completely
independent Wabi Authorities. This is infrastructure sharing, not federation.
The Authorities keep their own users, permissions, channels and databases.

The current controller is `scripts/wabi-media-node.py`. It has no third-party
Python dependencies. The `media-node` Compose profile packages that controller
with Wabi 1.x's reference LiveKit SFU so the normal operator path remains one
command even though multiple processes run internally.

## What you need

- a publicly reachable machine for the Media Node;
- a DNS/TLS endpoint that clients can use for the SFU, e.g. `wss://calls.example.org`;
- a LiveKit API key + secret stored **on the Media Node machine**;
- one `MediaRelay` pairing token generated by **each** Wabi Authority that may
  use this node.

The Wabi Authorities do not need public UDP and may remain behind NAT/CGNAT as
long as the Media Node can reach their HTTPS API. The Authorities never receive
the LiveKit root API secret: join tokens are minted on the Media Node and returned
through the authenticated outbound job relationship.

## 1. Create the config

Copy the example:

```bash
cp wabi.media-node.example.json wabi.media-node.json
```

Set the public SFU endpoint, region/capacity hints, and the Authorities you want
to serve. Every Authority entry needs its own one-time pairing token the first
time it joins.

Validate the file without making network requests:

```bash
python3 scripts/wabi-media-node.py --config wabi.media-node.json --check
```

## 2. Set LiveKit credentials

Generate strong, unique LiveKit credentials and place them in the Media Node's
`.env`:

```text
LIVEKIT_API_KEY=<media-node-key>
LIVEKIT_API_SECRET=<strong-random-secret>
```

Those variables are passed to the LiveKit container and the local Media Node
controller only. They are intentionally **not** copied into any Wabi Authority.
The controller uses them to mint short-lived room-scoped JWTs after an Authority
has already decided that a user may join/publish/subscribe.

Do not use the Compose placeholder value `disabled` for a shared node; the
controller refuses to start in shared mode with placeholder credentials.

## 3. Start the reference shared Media Node

The normal container path is one command:

```bash
docker compose --profile media-node up -d
```

That profile starts:

- the pinned self-hosted LiveKit reference SFU;
- `wabi-media-node`, the multi-Authority controller.

The current LiveKit profile exposes signaling on TCP 7880, ICE/TCP on 7881 and a
single WebRTC UDP mux port on 7882 by default. Put the public/TLS proxy and DNS in
front of the signaling endpoint appropriate to your deployment.

TURN remains separately selectable because not every deployment needs the same
TURN topology. When you intentionally use Wabi's coturn profile, configure its
required secret/public address and add `--profile turn` to the command.

For controller-only development, or when you operate the SFU separately:

```bash
LIVEKIT_API_KEY=... LIVEKIT_API_SECRET=... \
python3 scripts/wabi-media-node.py --config wabi.media-node.json
```

## 4. What the controller does

For every configured Authority it independently:

1. redeems that Authority's one-time token;
2. persists the returned Authority-specific node id/secret under
   `data/wabi-media-node/pairings.json` with private file permissions where the
   OS supports them;
3. heartbeats outbound using only that Authority's credential;
4. advertises the same physical SFU/provider/region/capacity;
5. claims only jobs the Authority assigned to that exact MediaRelay node;
6. activates the Authority's tenant-scoped room at the configured SFU endpoint;
7. mints short-lived LiveKit join tokens locally when the Authority requests
   `mint_token`;
8. reports the result using that Authority's own node credential.

After a successful first pairing, remove the consumed `pairingToken` from the
config. The persisted pairing is sufficient on later starts. Pairing tokens are
not copied into the controller's persisted state.

## 5. Trust boundary

A shared node intentionally has multiple credentials, but they are independent:

```text
physical Media Node
  pairing A -> Authority A node id + secret
  pairing B -> Authority B node id + secret
  pairing C -> Authority C node id + secret
```

Authority A never receives B or C's secret. A media job targeted to A's assigned
node id cannot be claimed by B's node identity. Job claims and job-result reports
verify the Authority-issued node secret and registered capabilities. Room
activation also requires the secret for the exact assigned MediaRelay node.

LiveKit root credentials remain local to the Media Node. The Authority sends only
an already-authorized request containing the opaque backend room, opaque user
identity, expiry and publish/subscribe grants. The returned JWT is scoped to that
exact room/identity.

The Media Node does not receive WabiDB state, chat history or user passwords.
Backend room names are the opaque tenant-scoped names produced by the Authority,
not human channel names.

## 6. Capacity and draining

The config can advertise:

- `maxRooms`;
- `maxParticipants`;
- `maxParticipantsPerRoom`;
- `acceptingNewRooms`;
- region and shared/private mode.

Authorities use these values to avoid selecting a node that explicitly declares
itself full or draining. Advertised totals are currently placement constraints,
not yet an atomic global reservation system across Authorities. Until hard shared
quotas land, operators should leave meaningful headroom rather than advertising
100% of physical capacity.

To drain a node, set:

```json
"acceptingNewRooms": false
```

and restart the controller. Existing SFU rooms are not forcibly terminated by
that setting; it prevents new placement once Authorities receive the updated
advertisement.

## 7. Current authorization boundary

The Authority's LiveKit token endpoint currently verifies:

- an authenticated non-bot account;
- current access to a Voice channel;
- assignment to an authenticated advertised LiveKit Media Node;
- current per-channel server mute/deafen state.

Server mute removes publish permission from the token; server deafen removes
subscribe permission. The remaining voice-policy work (muted-on-entry,
listen-only/stage speaking policy, and stronger binding to the exact admitted
voice session/device) must be completed before this is called the final voice
permission model.

## 8. Simple-setup target

The Compose profile is the first implementation of the one-command rule, not the
end of the setup UX. We should continue reducing required manual configuration:
public-reachability diagnostics, guided pairing, Call Doctor, TURN selection and
safe secret generation all belong in the product rather than in tribal knowledge.

The internal topology may contain multiple processes or containers; normal
administrators should not have to understand or configure each subsystem by hand.
