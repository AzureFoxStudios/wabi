# Community entry points (working-tree candidate)

One community may publish Authority and Anchor URLs for clients. The Authority derives a P-256 roster-signing key from its effective WabiDB root key. The public community ID is SHA-256 of that signing key's uncompressed public key. It is distinct from the Desktop Host Mode `server_id` shown in the host profile. A stopped full-instance restore that preserves the WabiDB root key preserves this community ID; creating a fresh server at the same address does not.

This feature is **discovery and cautious session routing**, not standby promotion, active-writer discovery or high availability. An Anchor still forwards canonical work to the single Authority. A roster can list a site that is offline, and its Authority entry can be stale after an outage. Never interpret the roster as a lease or a safe election result.

## Publishing

In the desktop app, open **Server Center → Infrastructure → Community entry points** while signed in as the community owner. Add one row for the current Authority and one for each Anchor, using a stable address that a member device can reach from its own network. For a three-site installation, the roofing/fabrication, materials/sales, and equipment-storage sites can each have a row. Enter the owner account password and select **Publish signed list**. The editor requests a fresh step-up proof, publishes a new roster version, and verifies the returned signature. Other admins can read the published list but cannot edit it. Reload displays the currently published list; the control does not probe whether a listed address is online or whether an Anchor is correctly connected to the Authority.

The entry-point list is for one community. A desktop client may connect to any reachable listed endpoint, but each Anchor still forwards canonical chat and API work to the current Authority. An address on a different site is useful for access and scoped helper traffic; adding its row does not copy WabiDB state or change the writer. An operator should verify the address from a device outside that site's LAN before sharing it with members.

A [disposable three-host Tailscale check](../testing/THREE_SITE_FIELD_2026-09-27.md) verified the Authority and both Anchors on separate computers and distinct public egress networks. It first failed when Iyoku's Authority chose a random port rejected by its existing firewall, then passed on its already-allowed TCP 3000. No firewall rule was changed. Choose and verify the actual application port at each site; Tailscale SSH reachability alone does not prove HTTP/WebSocket reachability. That check used HTTP clients on Ronin and Iyoku plus a local WebSocket harness, not the same Tauri desktop app at all sites. It did not test the signed roster's automatic HTTPS credential carry because the private HTTP addresses require manual sign-in.

Each Anchor can serve public, versioned `/_app/immutable/` frontend files from its embedded build without contacting the Authority. A missing version is forwarded to the Authority, so an Anchor with an older build can still load assets referenced by the Authority's current app shell while the Authority is available. The root app shell, its injected branding, APIs, uploads, and canonical data still come from the Authority or their separately documented cache paths. A local asset response has `X-Wabi-Anchor-Static: local` and a one-year immutable cache policy. It may still load while the Authority is down, but the community cannot use canonical chat or writes through that Anchor until the Authority returns. Keep Anchor and Authority binaries on compatible frontend builds during deployment, and measure actual site egress before claiming geographic bandwidth savings.

**Server Center → Infrastructure → Network health** probes the selected address's own `/health` route without sending a member token. It displays **Authority**, **Anchor**, or **Unverified** when that probe fails or returns an unknown role. An Anchor's local health result means that process responds; it does not check the Authority or prove that writes can continue. The CPU, memory, HTTP and interface measurements below it come from the Authority API, even when the selected address is an Anchor. Operator helpers have separate heartbeat rows. The published entry-point list names approved addresses, not their live status. An Anchor's public `/health` permits a cross-origin read for the desktop app and does not expose its private Authority URL.

For each Anchor, use an HTTPS `WABI_AUTHORITY_URL` when the upstream crosses a public network. Protected private/Tailcat IP HTTP requires the Anchor's explicit `WABI_ANCHOR_ALLOW_PRIVATE_HTTP=true` opt-in; that setting only permits the URL and does not establish the private transport. The member-facing public Anchor address also needs HTTPS. Anchor refuses URL credentials, paths, queries and upstream redirects to avoid forwarding member credentials to an unintended destination.

The registered owner obtains a short-lived step-up token with `POST /api/auth/stepup` and submits `PUT /api/community/roster` with the normal bearer token plus `X-Stepup-Token`. The body is:

```json
{
  "expectedVersion": 0,
  "entries": [
    { "nodeId": "site_a", "role": "authority", "url": "https://a.example" },
    { "nodeId": "site_b", "role": "anchor", "url": "https://b.example" },
    { "nodeId": "site_c", "role": "anchor", "url": "http://100.64.1.3:3001" }
  ]
}
```

`expectedVersion` starts at zero and must equal the current version for later updates. There must be exactly one Authority entry. URLs are origins with no path, credentials, query or fragment; node IDs are unique ASCII identifiers. Public addresses require HTTPS. Private IPv4/IPv6, loopback and `100.64.0.0/10` addresses may use HTTP for operator-managed private transport. New owner updates are durable WabiDB `community_roster_replaced_v1` events, with one incrementing version. On first startup after this change, an existing `community_roster.json` is imported once when WabiDB has no roster; later updates leave that legacy file unchanged. Once WabiDB has a roster, it is canonical even if the old file is stale or damaged. A member can read the signed roster at `GET /api/community/roster`; guests and bot accounts cannot. The endpoint is absent until the owner publishes a roster.

The owner's list is a trust decision: a listed endpoint can receive member traffic and credentials. Use an HTTPS endpoint whose certificate the client validates for automatic registered-member session carry. The candidate carries the current access token and account label, but does not yet migrate rotating refresh tokens; a member may need to sign in again after that access token expires. The client does not automatically carry credentials to plain HTTP, including Tailcat/private IPs, until the client can verify that transport's peer identity. Manual sign-in at such an address remains possible. A public IP can be used without a domain if its HTTPS certificate is valid for that IP.

The desktop Tailcat connection uses a temporary `127.0.0.1` proxy URL. It probes `/readyz` through the tunnel without credentials before switching, then reloads and asks the member to sign in at that URL. It remembers the prior address and restores it on disconnect or after an app restart when the native tunnel is gone. The local proxy port is reserved before the native command returns. These checks improve route reliability; they do not bind the Tailcat peer to a signed roster entry or authorize copying a prior session token to the proxy. The app still needs a real cross-network test of this path.

The signed response contains `body`, `publicKey` and `signature`. The signature is ECDSA P-256/SHA-256 over the UTF-8 JSON serialization of `body`, with raw 64-byte `r || s` signature encoding. The client verifies the key hash, signature, exact URL list, monotonic version and seven-day expiry. It pins a community key per account and URL. A different server reusing a previously pinned URL cannot silently replace that key. The first roster from an already authenticated server is trust-on-first-use; operators should publish it before handing out alternate addresses. Once members have a valid cached roster, they can try another listed HTTPS address if the original one is unavailable, within the expiry window. Revoking a compromised endpoint cannot recall older signed rosters already cached by offline clients, so revoke affected member sessions as part of incident response.

The legacy sidecar remains in a stopped full-instance snapshot; preserve it while older backups and binaries may still use it. After migration, the WabiDB event is the roster source and the old file may be stale. A [disposable fenced-receiver check](../testing/DB_REPLICA_PROCESS_2026-09-27.md) caught up a later roster event, published upload bytes and selected sidecars when their optional lanes were configured. That receiver still lacks a complete cross-file recovery point, cannot serve clients, and cannot be promoted. An Anchor has no independent authenticated roster cache or live-writer discovery. Operators must publish reachable alternate URLs before a planned move and let members cache the signed list while the Authority is healthy. A rollback to an older binary can see the stale legacy file and must use a matching stopped backup or an explicit migration procedure; do not assume the new event replays on an old binary. The client still stores some local state per URL, so endpoint switching needs an explicit three-site check for duplicate drafts, offline queue replay, optimistic message IDs and notifications.
