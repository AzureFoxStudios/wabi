# Controlled move from a caught-up passive copy — 2026-09-27

**Scope:** Disposable single-computer loopback process check of main Wabi. This is a planned move with the old Authority under operator control. It is not recovery after an unreachable node or a three-network field result.

The process check used a real Authority, two Anchors and a fenced `wabi-db-replica-dev` receiver. It exported an encrypted stopped baseline, resumed the Authority, then replicated a later message and a 4,096-byte upload. The receiver advanced from applied/indexed commit 17 to 19, verified the upload SHA-256 `495b63b9b5c41b598d95c9b884215a755c800e1994630244c7b80498b719049c`, and still reported `writerFenced: true` and `fullInstanceReady: false`.

After stopping both processes, the source and passive trees had no one-sided files. The only unequal raw file was `wabidb/projections/snapshot.json`; its decoded, order-normalized state matched at watermark 19 with 11 indexes and 33 entries. The receiver left an **empty** `uploads/.replica` staging directory after the completed upload. The test removed it with `rmdir`, which would refuse a nonempty directory. The new whole-tree comparison then matched.

The test fenced the stopped old Authority and sealed a private receipt for its exact data/uploads tree and normalized projection state. Activation without the external-state review assertion was refused. Activation with the receipt and assertion removed the passive writer fence; the old tree kept its fence and refused full Authority startup. The replacement Authority reached readiness behind the same Anchor URL, preserved community ID and an existing member session, returned the prior message history and upload bytes, retained the later replicated message, and accepted a new write.

A follow-up run with the frontend-embedded development binaries also passed and recorded `plannedCutoverMs: 530`. The timer starts immediately before stopping the old Authority and ends after the replacement Authority and known member-facing Anchor report readiness. It includes receiver shutdown, state comparison, fencing, receipt transfer within one machine, activation and process startup. It is one loopback **planned cutover elapsed-time sample**, not observed user outage, an inter-site recovery-time objective, or unexpected-node-loss recovery. No acknowledged fixture message was missing in the follow-up read; this does not establish a general zero-loss recovery point objective.

A further run exercised deletion and revocation before the move. The Authority acknowledged a durable message deletion and an owner upload revocation. The harness read the Authority's post-revocation commit position and waited until the fenced receiver applied and indexed through that position and reported upload pruning through its applied position. Its upload registry matched the source, and the revoked 4,096-byte file was absent from the passive tree. After the controlled move, the deleted message stayed absent from API history and the revoked upload URL returned HTTP 410. The receiver advanced from commit 17 to 22; the stopped trees had no one-sided files, and the order-normalized projection snapshots matched at watermark 22 with 12 indexes and 41 entries. This run recorded `plannedCutoverMs: 1081`, another single-computer sample. The receiver's pruning watermark by itself only describes the commits it has seen; it must be compared with the source's later commit position before treating cleanup as current.

A subsequent run added a channel-wide clear. The owner created a separate durable-history channel, sent a message, received `channel-messages-cleared` only after the new `channel_messages_cleared` event committed, and found that channel empty on the source. The fenced receiver caught up from commit 17 to 27. After the planned move, the same channel was still empty, while messages in the original channel and later new writes remained available. The stopped trees again had no one-sided files; their order-normalized projections matched at watermark 27 with 12 indexes and 51 entries. This run recorded `plannedCutoverMs: 1184`, a single loopback sample. The focused channel-clear check also passed: when the writer was fenced, the server returned `clear-channel-error`, kept the live view, and left durable history visible.

A later loopback run added a five-second retention canary in a separate channel. The follow-up check confirmed that the message appeared in REST history before expiry, then waited until the Authority's history no longer included it, read the Authority's later commit position, and waited for the fenced receiver to apply and index through it before the planned move. The expired channel was still empty after activation. The receiver advanced from commit 17 to 32; the stopped trees again had no one-sided files, and normalized projections matched at watermark 32 with 12 indexes and 61 entries. The follow-up recorded `plannedCutoverMs: 507`, another single-computer sample. This is one expiry fixture, not proof of every retention mode, large backlog or secure erasure.

The same change made Socket.IO durable-message deletion wait for WabiDB confirmation before removing the session copy or emitting `message-deleted`. If the durable writer is fenced, the client receives `delete-error` and the message remains visible. A focused regression check passed for that failure and for session-only live-message deletion.

The focused `wabi-instance-snapshot` tests also passed: 13 tests covered encrypted export/restore, locks, paths, source fencing, receipt tampering, changed/extra files, changed projection state, and successful activation. The disposable process run removed its temporary roots on exit.

This establishes a **guarded planned move at one stopped boundary** for the exercised fixture, including individual and channel-wide current-view deletion, one timed-expiry canary and active/passive upload denial. It does not show a shared live cross-file checkpoint, completeness for every optional/plugin/external store, secure erasure of raw history/caches/backups, all retention modes or backlogs, a remote old-host fence, automatic election, or a physical three-site trial. The receipt uses the persisted root key held by both copies; it is a workflow check, not remote attestation. Operators must independently keep the old host stopped and fenced and review external state before activation.
