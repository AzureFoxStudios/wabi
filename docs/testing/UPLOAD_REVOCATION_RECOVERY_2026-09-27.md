# Upload revocation persistence check

**Date:** 2026-09-27  
**Scope:** Disposable upload registry files, first boot, resumable upload publication, and an existing volunteer-delivery contract. This checks local revocation and publication safety, not cross-site upload replication or physical deletion.

```bash
cargo test --locked -p wabi-server --lib upload_registry::tests
cargo test --locked -p wabi-server --lib api::upload::tests
cargo test --locked -p wabi-server --test resumable_upload_contract
cargo test --locked -p wabi-server --lib api::whiteboard::tests
cargo test --locked -p wabi-server --test first_boot_onboarding
cargo test --locked -p wabi-server --test volunteer_boosters_contract
cargo test --locked -p wabidb --lib projections::upload_revocations::tests
cargo test --locked -p wabi-server --test db_replica_process_contract stopped_encrypted_baseline_then_verified_upload_catch_up
```

The eight registry tests, the focused upload route tests, and the end-to-end resumable upload contract passed. Earlier checks passed ten whiteboard unit tests, fourteen first-boot tests and the volunteer-delivery contract. A valid registry reloaded its upload entries and revocation. A malformed registry was refused instead of loading as empty, which would have forgotten revoked filenames. A deliberately blocked registry save returned an error while the in-memory revocation continued to deny access; after removing the obstruction, a repeat revocation saved the state and it survived reload. An empty fresh uploads directory started without a registry, while a nonempty uploads directory without its registry refused Authority startup. Registry updates use a private temporary file, file sync, atomic replacement and parent-directory sync on Unix. New upload bytes stay in an unserved staging path until their registry entry is durable; a failed save does not publish the final file. Resumable chunks serialize per upload, append at the current offset, cannot exceed the declared size, and have an 8 MiB request limit even under the full server's larger default. Completion rejects partial or mismatched disk bytes, syncs the staged file, saves the registry, renames the file, and syncs the uploads directory on Unix before acknowledging it. A failed publication keeps the session so the client can retry. Owner deletion records the revocation before removing bytes, and the whiteboard-specific file route checks revocations too.

Two projection checks passed for the versioned, bounded `upload_revoked_v1` event. Two new registry checks passed: legacy JSON-only denials are imported into WabiDB, repeated revocation does not append another event, and a committed denial repairs a stale or unsuccessfully saved JSON registry. A focused first-boot check passed through the actual Authority startup path. A two-process check passed after an encrypted stopped baseline: the fenced WabiDB receiver applied the later denial at sequence 4, then a reopened passive database repaired its stale registry. This is a revocation decision crossing the incremental database path, not an upload file transfer.

The `/uploads/` URL is still a capability URL, and a revoked file's bytes may remain on disk or in caches/backups. A missing registry is accepted only when the uploads directory is absent or empty. The startup guard cannot detect a deliberately replaced but valid empty registry for revocations that were never imported into WabiDB, or old bytes placed in the uploads directory after startup. The directory sync improves local publication durability but is not a power-loss proof or a shared checkpoint with WabiDB. The event does not prove secure erasure, incremental upload bytes/metadata or other sidecar replication, or a recoverable standby. Operators must restore `upload_registry.json` with its matching upload tree and other Authority state; deleting or replacing a damaged registry is not a safe recovery step.

**Later follow-up:** The [expanded two-process check](DB_REPLICA_PROCESS_2026-09-27.md) now covers optional verified upload-byte copying and current-tree removal of revoked files after WabiDB catch-up and receiver restart. A separate opt-in lane copies a fixed set of top-level sidecars, including the upload registry, but has no shared checkpoint with WabiDB or uploads. Neither path erases caches/backups or establishes a recoverable standby. The counts and limitations above describe the earlier local check.

The [real Authority plus two-Anchor preflight](THREE_SITE_REAL_AUTHORITY_PREFLIGHT_2026-09-27.md) found a fresh-boot conflict with this guard: the server created an empty uploads `.tmp` directory before checking for a missing registry. Startup now creates staging after the guard, and a focused unit check permits only an empty, real `.tmp` left by an earlier attempt. A populated staging directory or actual uploaded file without the registry still refuses Authority startup.

**Publication crash follow-up:** The full Authority first-boot suite passed 19 tests, including two simulated crashes after a canonical publication commit and before final rename. Startup finished both direct and resumable staging formats after matching the committed size and SHA-256. A changed staged file blocked startup; an uncommitted staged file remained private. A separate check rejected changed final bytes even while the local registry remained current. All ten upload-registry unit tests and the resumable upload contract passed after the change. The source now syncs the staging directory before committing publication and verifies every canonical published file's digest at startup. This is a local recovery boundary, not a power-loss experiment, a live standby, or a performance result for a large upload tree.
