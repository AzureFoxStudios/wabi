# Regional upload cache loopback receipt — 2026-09-27

## Scope

This checks an opt-in Anchor RAM cache for canonical attachment downloads. The processes ran on one machine over loopback. It is a development check, not a three-site bandwidth or privacy acceptance result.

## Checked

- `CARGO_INCREMENTAL=0 cargo test --locked -p wabi-server --lib anchor::tests`: 17 Anchor tests passed with local listener permission. The cache case used two independent Anchors and a mock Authority. Each Anchor made one origin GET for its first download and served its second download after a fresh HEAD check. The mock counted two GETs and four HEADs in that initial phase. The mock then changed its policy to `no-store`: two repeat requests fetched from the Authority, neither carried a cache-hit header, and returning to `no-cache` produced a new miss. Policy checks rejected a missing policy, qualified `no-cache` and a separate `no-store` header; a mixed-case client `NO-STORE` header also bypassed the cache. A request without the required bearer token was denied, revocation blocked both caches, a later allowed request refilled them, and Authority loss returned 503. A separate test checked bounded eviction.
- `cargo test --locked -p wabi-server --test regional_upload_cache_contract`: a real Authority router supplied a canonical published upload to an Anchor. The first download was a cache miss, the second a hit with the same bytes, and a durable revocation caused the next request to return 410. The two requests used different allowed browser origins; each response carried the fresh origin-specific CORS header.
- The real Authority/Anchor contract was rerun after the cache-policy tightening with `CARGO_INCREMENTAL=0`; its one integration case passed again. The `no-store` transition itself was exercised by the mock Authority in the focused Anchor suite above.
- `cargo test --locked -p wabi-server --test first_boot_onboarding upload_head_and_conditional_get_recheck_revocation`: the Authority's HEAD and conditional GET expose the canonical digest and recheck revocation; legacy files are marked `no-store`.
- `node scripts/tests/revocable-media-sw.test.mjs`: the service worker removes its old media cache and fetches revocable uploads and whiteboard files without an offline stale response.
- `node scripts/three-site-real-authority-smoke.mjs target/debug/wabi-server`: a disposable loopback TCP meter sat between the equipment Anchor and the Authority. For a 262,144-byte upload, the first download (`miss`) received 263,175 Authority-to-Anchor TCP bytes; the repeat (`hit`) received 504 bytes for revalidation. The corresponding Anchor-to-Authority counts were 1,099 and 550 bytes. The same run kept the Authority-loss check: a cached file returned 503 while the Authority was down. These counts include HTTP headers and reflect one local run, not a WAN bandwidth measurement.

## Result and limit

The local checks establish that a repeat eligible upload can avoid one Authority **file GET**, while each Anchor still asks the Authority for current availability and digest on every request. The real `/uploads/` route is URL based; it does not enforce per-member file access. The mock's bearer-token denial checks forwarding behavior, not a current product ACL. The Authority must remain available; this is scoped byte offload, not recovery or local chat processing. A downloaded client copy, browser cache outside this worker, backup or crash dump cannot be erased by revocation. There is a short HEAD-to-delivery revocation race to characterize before a stronger privacy claim.

The [three-computer follow-up](THREE_SITE_FIELD_2026-09-27.md#follow-up-byte-metered-three-computer-run) used a meter on each Anchor's upstream path. On the equipment path, a 262,144-byte file cost 263,175 Authority-to-Anchor wire bytes on a miss and 504 bytes on a hit. Both Anchors' sampled 28,424-byte embedded app asset requests caused zero upstream bytes. A fresh egress check found that iRonin and Iyoku share a public IPv4 egress and a local LAN path, so this does not establish three independent physical site uplinks. Gate A still needs the actual three-network placement, real desktop clients, sustained traffic and media measurements; Gates B–D require separate state, leadership and room ownership work.
