# Two-process fenced WabiDB catch-up check

**Date:** 2026-09-27  
**Scope:** Disposable loopback sender and a separate fenced WabiDB-only receiver process. No physical remote site or full Authority standby.

Focused commands:

```bash
cargo test --locked -p wabi-server --bin wabi-instance-snapshot
cargo test --locked -p wabi-server --test db_replica_process_contract -- --nocapture
cargo test --locked -p wabi-server --lib instance_sidecars::tests
cargo test --locked -p wabi-server --test community_roster_contract
cargo test --locked -p wabi-server --test first_boot_onboarding
cargo test --locked -p wabidb --lib projections::community_roster::tests
cargo test --locked -p wabidb --lib projections::upload_revocations::tests
cargo test --locked -p wabidb --lib projections::upload_assets::tests
cargo test --locked -p wabi-server --lib upload_registry::tests
cargo test --locked -p wabi-server --test upload_backfill_contract
cargo test --locked -p wabi-server --test resumable_upload_contract
cargo test --locked -p wabi-server --lib peer_endpoint_requires_https_or_explicit_private_transport
cargo test --locked -p wabidb configured_replication_refuses_missing_transport_before_creating_data
```

The snapshot binary's 11 tests passed, including a restore that checks the passive writer fence exists before the restored directory is published. Five two-process checks passed on loopback:

1. A source WabiDB engine sent two commits through the real HTTP transport to `wabi-db-replica-dev`; a missing token returned 401 and a mismatched root-key fingerprint blocked the sender. The receiver applied both commits. It was stopped, a third commit was made at the source, and the restarted receiver caught up to sequence 3. After stopping the receiver, reopening its WabiDB still showed the third event in its projection. The reported applied and indexed sequences matched at each observed catch-up point.
2. A source with a real WabiDB commit, upload registry, upload and notes sidecar was stopped and exported with `wabi-instance-snapshot`. The encrypted archive restored into a fenced passive tree. Its receiver started at applied sequence 1; after the source reopened and wrote a second commit, it caught up to sequence 2. A later versioned community entry-point roster event reached sequence 3. A later `upload_revoked_v1` decision reached sequence 4. The configured receiver removed the revoked baseline file, including a stale copy placed back in its tree before restart. A later upload's `upload_published_v1` metadata, size and SHA-256 reached sequence 5. With upload trees explicitly configured, its 2 MiB plus 3 byte file then arrived through multiple 1 MiB chunks and matched the original bytes. A registered legacy file added after baseline was explicitly backfilled into a publication event at sequence 6; the receiver copied and verified its bytes. With the explicit sidecar lane enabled, the upload registry also arrived with its revocation and legacy entry. A notes change made without another database commit reached the passive tree, and later source deletion removed that passive notes file. The receiver rejected unauthenticated sidecar inventory, an unlisted name, a wrong request hash, and a symlinked destination without changing its target. This proves a narrow eventual file-copy path, not whole-instance recovery.
3. Two databases used the same root key and each reached commit sequence 1 with different first commits. The receiver reported a different canonical commit-prefix fingerprint. After the sender wrote sequence 2, repeated sync cycles left the divergent receiver at sequence 1. The sender now compares that prefix before it skips any earlier commits.
4. A sender with committed entries 1, 2 and 3 intentionally submitted entries 1 and 3. Its push carried the genuine fingerprint through entry 3. The fenced receiver rejected the incomplete batch before applying any commit, then accepted all three entries when sent together. A separate unit check covers a legitimate numeric gap caused by a failed command and a retry after partial progress. The rule is a matching commit-index prefix, not adjacent numeric sequence values.
5. A fenced receiver accepted only authenticated upload requests and rejected a request over the 1 MiB body limit and a wrong starting offset. It staged the first two bytes of a five-byte file, restarted, and reported offset 2. A wrong final chunk failed SHA-256 verification and left no published file. It then restarted from offset 0 and published only the correct bytes. A second file was partially staged and then revoked; after the revocation commit reached the receiver, its staging chunk was removed and a further upload chunk returned 410.

All tests use disposable synthetic community data and a shared test key, not hosted data or a full running Authority. The second test covers a stopped baseline plus later database, upload and allowlisted sidecar changes. The sidecar lane has no shared ordering boundary with database commits or upload publication, and its inventory does not report a recovery checkpoint. The prefix check hashes commit-index entries, not all historical segment contents or the complete instance. These tests do not cover secure erasure from caches/backups, retention expiry, sustained traffic, large files, root-key rotation, field networks, active Authority failover, or promotion. Database segments still travel in buffered JSON; the upload inventory iterates the publication projection and verifies existing files, so no capacity result follows from this check. A matched WabiDB position and copied files are still incomplete-instance evidence.

A focused `first_boot_onboarding` check imports a legacy `community_roster.json` into WabiDB, updates it to version 2, rejects a stale version request, then reopens from WabiDB while the legacy file is stale and again when it is damaged. The later full first-boot suite passed 19/19, including reconstruction of a missing canonical upload entry from matching bytes and refusal of a same-size file with the wrong hash. The owner-facing roster contract passed, and two WabiDB roster projection checks passed, including rejection of skipped or repeated versions. Two upload-publication projection checks passed as well. This proves the Authority's local roster source changed and that an isolated Authority startup can repair a narrow upload sidecar gap; a safe promotion path and whole-instance recovery remain unproven.

The focused WabiDB startup check passed: configuring replication without an explicit transport fails before creating the data directory. It cannot report a successful no-op send as replication progress.

A later [state-comparison follow-up](REPLICA_STATE_COMPARISON_2026-09-27.md) changed the receiver to drain on SIGTERM/Ctrl-C. The focused receiver-restart process check passed with a graceful final stop, a projection snapshot, no remaining WabiDB lock, and the later event still present after reopening. A disposable local Authority/receiver run also compared the stopped fixture trees and decoded projection snapshots; that does not broaden the receiver into a complete standby.

For the publication record change, both `upload_assets` projection checks, all 13 upload-registry checks, the resumable-upload contract, and all 5 two-process checks passed. The resumable contract confirms a successful completion has a projected size/hash. Registry checks confirm an identical retry keeps its creation timestamp, conflicting reuse of a filename is refused, and stale metadata is rebuilt only after matching bytes are verified. The process checks confirm both a new upload and an explicitly backfilled registered file crossed to the fenced receiver when the optional byte path was enabled. The disposable `upload_backfill_contract` command check passed preview, apply and fenced-data refusal. The receiver still reports `fullInstanceReady: false`; `uploadPrunedThroughCommitSeq` reports the separate current-tree revocation cleanup position, while sidecars have no equivalent watermark. Two sidecar allowlist/digest unit checks and five updated process checks passed on 2026-09-27.
