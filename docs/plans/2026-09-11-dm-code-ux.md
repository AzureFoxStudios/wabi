# DMs, independent-server friends, and shared code: UX implementation contract

Approved direction: substantial UX/UI redesign is permitted. Existing AI-generated layouts are not constraints. Preserve useful functionality, accessibility, theme compatibility, and Wabi's independent-server design, not inconsistent old screens.

## This branch: first implementation batch, not the complete audit closure

- One DM inbox (`DmHub`) serves center and side placements: labeled New message, searchable people, All/Unread/Pinned filters, personal pin ordering, explicit row overflow, and preserved group creation/personal notes.
- Both conversation placements use `DmConversationHeader`: name plus inspectable handle/host, bounded call/video controls, a panel-placement icon instead of a star, and separate group actions. Moving into another placement is described as **Open**, not a promise to move every draft and scroll state.
- Privacy information states the actual server-readable model. These screens no longer expose local Sealed/Private/Open controls as encryption. Shared DM channel deletion is intentionally removed from ordinary inbox cleanup; closing a view is not deleting another person's conversation. Group leave retains its confirmed server operation.
- DM selection uses the existing #183 resolver, strengthened to reject errors/empty IDs/mismatched returned participants. Canceled or stale inbox requests cannot open a new surface. No placeholder is manufactured from a failed creation.
- The compact code panel has local, account/server/channel-scoped data. It does not borrow the global Lore store's mutable context. Late file responses cannot overwrite another selection. Dirty edits guard file selection. Navigating to another channel keeps an active editor on its original project until the user leaves it explicitly. Mirror/role presentation follows the main workspace's existing gates; the server remains the authority.
- The file viewer separates published content and private editor drafts. It checks project review policy on edit entry, labels Publish revision vs Submit for review, keeps draft status visible at narrow widths, offers comparison and draft download during conflicts, and preserves the editor instance/cursor/undo history on successful publication.
- The editor theme follows Wabi tokens rather than forcing a dark theme. The syntax primitives are already present as CodeMirror/Lezer dependencies in the existing lockfile; no packages or versions are upgraded in this batch.

## Important limits

This is not a deployment or a complete security sign-off. The main ChatComposer and the side DMMessageView remain distinct internally to preserve payments, notes, mentions, and Line-style customization. Their drafts/replies/attachments/search/unread/typing behavior still needs a shared conversation controller and end-to-end tests. The inbox changes do not repair every upstream createDM protocol correlation problem, privacy-mode reference elsewhere, profile/member call path, attachment endpoint, or server authorization policy.

No cross-server friend service or remote live-draft service is implemented by these UI changes. Do not present local draft status as another person's live activity. The compact panel's internal navigation is guarded; this is not yet a universal dock-close/navigation guard or persistent draft recovery system. A browser reload still relies on the unsaved-change warning. A pending-review editor view is not a review-branch browser.

## Approved friends 1.5 direction

Friends are client-owned contacts with explicit server/account endpoints. Servers remain independent: no shared server identities, memberships, roles, bans, channel histories, automatic routing, or replicated social graphs. Every conversation has an inspectable hosting server. Never automatically merge identities by name/avatar, reuse credentials on another host, or reveal someone's other communities through presence.

Distinguish a privately saved contact, an accepted friendship, and a verified linked account. Same-name accounts require explicit linking and proof for any verified claim. No common conversation host means an explicit invitation/route, not a fake delivered message. Cache and draft keys include server and account; logout retires old-session work. Offline and last-known presence must not appear globally live.

## Approved shared code direction: a drive for code

Keep project/file navigation, permissions, editor identity, draft state, and actual changing code in one coherent workspace. Authorized collaborators must eventually see the real live draft or diff, not merely a status dot. Published content remains separately selectable and publication/review is deliberate. Do not require a simultaneous multiwriter merge engine just to provide authorized read-only observation of a writer's live draft.

A future live session needs server-authenticated identity and resource permission checks, explicit draft audiences, sequence/version validation, bounded payloads, heartbeat expiry, reconnect recovery, revocation, and conflict-safe publication. Draft text is content, never executable HTML or JavaScript. Only approved shared resources participate; private notes, unsent messages, tokens, and settings are not globally announced. An external filesystem watcher sees saved bytes, not unsaved editor buffers; unsaved external editing requires an explicit integration.

## Required acceptance gates

1. DM: starting from a person or inbox, new/existing/offline recipient, canceled/failed request, two concurrent opens, reconnect, same-account re-login, server switch, unread/pinned filters, unknown member, group settings/leave, and all placements. Closing an inbox/view must never delete a shared transcript or steal focus on the recipient's device.
2. Code: A/B slow response race, file/project switching while dirty or saving, save while continuing to type, failed save, changed server etag, compare/export, review-required project, read-only mirror, role change, logout/server switch during every async operation, wide/narrow pane, and universal close/draft-recovery gaps above.
3. Live collaboration: two authorized accounts observe actual changing content; an unauthorized third account sees neither contents nor private filenames/activity. Revocation and disconnect remove stale presence; private drafts remain private. These are future-service tests, not claimed results of this batch.
4. Visual/accessibility: real application screenshots in light/dark/custom themes, 320/480/wide panes, long handles/project/file names, keyboard-only navigation/focus return, 200% text, touch hit targets, and mobile keyboard plus call overlays. Component fixtures are helpful but cannot replace a full-application pass.

## Checks

From `frontend/`:

```sh
node --experimental-strip-types --test scripts/dm-code-ux.test.mjs
node scripts/dm-code-ux-compile.mjs
npm run check
npm run build:static
```

The dependency-free tests exercise production presentation/intent helpers and explicit source-wiring contracts. Compiler tests compile actual changed Svelte markup for client and server. Neither proves live network, authorization, calling, CodeMirror browser integration, or deployment. Record actual local/CI/browser outcomes in the PR rather than assuming success.
