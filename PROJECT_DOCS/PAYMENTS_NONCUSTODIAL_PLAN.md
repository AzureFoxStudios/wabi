# Wabi Payments Plan (Non-Custodial, Plugin-Driven)

Last updated: 2026-03-08
Status: Core backend + frontend payment sheet + `th-payments` contracted-adapter flow + signed-only rollout path implemented
Owner: Core backend + plugin platform

## 1) Goal

Enable Wabi servers to offer payment actions (QR, links, app handoff, optional tap flows) while keeping Wabi out of money custody and bank/operator roles.

## 2) Hard Boundaries

Wabi core must:
- Never hold user funds.
- Never provide stored-value wallet balances.
- Never provide internal P2P money transfer ledger.
- Never present itself as a bank, money transmitter, or payment institution.

Wabi core may:
- Create and track payment intents.
- Render payment artifacts generated by provider plugins (URL, QR payload, app deep link).
- Reconcile status from signed provider webhooks.

## 3) Explicit Exclusions

The following are out of scope unless future policy changes are explicitly approved:
- FedNow integration.
- CBDC / "digital dollar" style rails (DUSD or similar).
- Any Wabi-managed custodial crypto wallet model.

## 4) Architecture

### Core (always present)

- `payment_intent` lifecycle state machine:
  - `draft`
  - `pending`
  - `succeeded`
  - `failed`
  - `expired`
  - `refunded`
  - `disputed`
- Idempotency enforcement for create/update/refund callbacks.
- Signed webhook verification framework.
- Immutable payment audit log.
- Capability resolver to choose the best methods for the current user context.

### Plugins (actionable rails)

Region/provider plugins implement the rails and compliance specifics:
- Thailand plugin: PromptPay QR + optional international wallets/cards.
- North America plugin: cards + ACH/pay-by-bank.
- Japan plugin: cards + local methods (for example PayPay/Konbini via provider support).
- China inbound plugin: WeChat/Alipay style rails (where provider contracts allow).
- Crypto plugin: non-custodial processor flows only.

## 5) Regional UX Policy

Do not hard-lock to a single local rail.

Method ordering policy:
1. Show top "Recommended" methods using region + currency + device + historical success.
2. Keep an "All methods" list available.
3. Hide rails below `<1%` usage by default unless admin-pinned.
4. If a Western method is valid in Bangkok (or vice versa), show it naturally when eligible.

## 6) Bank Coverage Strategy (NA)

Do not build per-bank adapters (Wells Fargo, BoA, Redwood CU, etc.).

Use bank-agnostic rails:
- Card networks and wallets.
- ACH/pay-by-bank through regulated PSP/aggregator support.

Result: customers of major and smaller banks can still pay without one-off bank integrations.

## 7) Desktop + Mobile/NFC Policy

- Desktop-first checkout flows are required.
- Mobile native (Tauri) may add:
  - NFC/tag interactions where applicable.
  - App deep-link handoff and return callbacks.
- "Tap to pay" must be implemented through licensed PSP SDKs/capabilities, not raw generic NFC assumptions.

## 8) Payment Plugin Contract (v1)

Each plugin must declare:
- `plugin_id`, `provider_name`, `version`
- supported `countries`, `currencies`
- `checkout_modes`: `qr`, `payment_link`, `app_switch`, `tap_to_pay`
- webhook signing/verification requirements
- refund/dispute capability flags
- operator requirements (merchant account, keys, onboarding notes)
- compliance metadata (jurisdiction notes, prohibited flows)

Required runtime methods:
- `createIntent(input) -> provider_artifact`
- `presentIntent(input) -> presentation_data`
- `verifyWebhook(input) -> normalized_event`
- `getIntentStatus(input) -> normalized_status`
- optional `refundIntent(input) -> normalized_status`

## 9) Security And Compliance Controls

- Secrets never exposed to frontend.
- Webhook signatures required for state transitions.
- Strict idempotency keys for all mutation paths.
- Replay-safe webhook processing.
- Region/currency deny-list + allow-list controls.
- Payment access policy gates in backend:
  - global `enabled` switch
  - role allow-list (`allowedRoleNames`)
  - per-user payment block override
- Clear operator/legal disclaimers in admin UI and docs.

Note: this document is technical policy, not legal advice. Final launch requirements must be reviewed by qualified counsel for target jurisdictions.

## 10) Rollout Order

1. Core payment intent framework in backend (non-custodial only).
2. Provider-agnostic frontend payment sheet with capability resolver.
3. Thailand plugin first (PromptPay QR baseline).
4. NA plugin second (cards + ACH/pay-by-bank).
5. JP/CN plugins based on provider contract readiness.
6. Crypto plugin last, non-custodial only.

## 11) Country Plan (v1)

### Thailand (`th-payments`)

Primary methods:
1. PromptPay QR (merchant-presented Thai QR standard).
2. Card and wallets via provider checkout.
3. Payment link fallback (shareable URL/QR).

Presentation requirements:
1. Render large on-screen QR.
2. Show `Save QR` and `Share` actions prominently.
3. Show payment countdown/expiry and refresh action.
4. Show status polling + webhook-confirmed completion.

Notes:
1. Thailand usage is heavily QR-centric; this method should rank first by default in THB/TH.
2. "Open bank app" can be offered as optional app handoff where supported by provider/device; QR scan remains universal fallback.

### North America (`na-payments`)

Primary methods:
1. Card checkout (desktop and mobile).
2. Wallets (Apple Pay / Google Pay where available).
3. ACH / pay-by-bank.
4. Shareable payment links and invoice-style links.
5. Optional PayPal.

Notes:
1. Do not integrate per-bank APIs (Wells Fargo, BoA, Redwood CU, etc.).
2. Use bank-agnostic rails so most banks/credit unions are covered.
3. Zelle should be treated as bank-app-native transfer rail, not core merchant checkout default.

### Japan (`jp-payments`)

Primary methods:
1. Card and wallets.
2. PayPay (where provider account supports it).
3. Local convenience methods via provider support.

### China Inbound (`cn-inbound`)

Primary methods:
1. WeChat Pay.
2. Alipay.
3. Card fallback where applicable.

Notes:
1. Enable only when merchant/provider contracts and jurisdiction requirements are satisfied.
2. For Thailand tourism use cases, support can ride through Thailand QR cross-border schemes where available.

## 12) Platform Flow Plan

### Desktop

1. User chooses method in payment sheet.
2. Wabi creates non-custodial intent via plugin.
3. Plugin returns one of:
   - QR payload/image
   - hosted payment link
   - provider redirect URL
4. Wabi shows status: `pending -> succeeded/failed/expired`.
5. Webhook signature verification is required before terminal state.

### Mobile (Tauri)

1. Same intent flow as desktop.
2. If plugin supports app handoff, show `Open App` deep-link button.
3. If deep-link fails or app missing, fall back to QR or hosted link.
4. If platform/provider supports tap flows, use provider SDK path only.
5. Return callback/deep-link updates intent status in app.

## 13) Method Ranking Rules

1. Rank by region + currency + device + historical success.
2. Show `Recommended` list first.
3. Show `All methods` list always.
4. Auto-hide methods below `<1%` usage unless admin-pinned.
5. Never hide a valid user-preferred method already used recently by that user.

## 14) Immediate Build Steps

2. Add `payment_intents` table and immutable `payment_events` audit table.
3. Add `/api/payments/*` endpoints:
   - create intent

4. Build frontend payment sheet with:
   - method ranking resolver
   - QR renderer
   - save/share controls

5. Implement `th-payments` plugin first with PromptPay QR + link fallback.
