Getting serious build issues in both frontend and backend.

You’re failing at runtime because your container is trying to execute node build, but /app/build isn’t there (or isn’t a runnable entry file).

What the evidence says

The process being run is node build. 

Node then errors: “Cannot find module ‘/app/build’”. 

Your build script produces a single output file named build (no extension): --outfile=build. 

So either:

The build artifact never exists at runtime, or

Something overwrites /app after image build (very common with bind mounts), or

You’re actually running the wrong image/container (your log says wabi-frontend, not wabi-backend). 

Most likely causes (in practice)

docker-compose / docker run is bind-mounting your source over /app (e.g. .:/app).

That replaces the image’s /app (including the built build file) with your host folder. If your host folder doesn’t have a build file, Node can’t find /app/build.

Wrong context / wrong service is running

The log shows wabi-frontend@1.0.0 start even though the backend package you shared is wabi-backend. 

That usually means your backend container is accidentally built from the frontend directory, or you’re looking at the frontend container logs.

Ambiguous/fragile output naming

Outputting a file named build (no .js/.mjs) works only if everything lines up perfectly, but it’s easy to break (and confusing because many projects have a build/ directory).

Concrete fixes

Fix 1 (recommended): make the backend output a real file path and run that

Change package.json to something unambiguous:

{
  "scripts": {
    "build": "esbuild src/server.ts --bundle --platform=node --target=node24 --format=esm --outfile=build/server.mjs --external:socket.io --external:better-sqlite3",
    "start": "node build/server.mjs"
  }
}


This removes “is build a directory or a file?” ambiguity and makes the entrypoint explicit. (Right now you’re doing --outfile=build + node build 

.)

Fix 2: stop overwriting /app in production

If you have something like this in compose:

volumes:
  - .:/app


remove it for the production container (or create a separate docker-compose.dev.yml that mounts the source).

Fix 3: verify you’re running the backend image you think you are

Run these checks:

docker compose ps
docker compose logs <backend-service-name>

docker run --rm <backend-image> ls -la /app
docker run --rm <backend-image> ls -la /app/build*


If /app/build (or /app/build/server.mjs after Fix 1) is missing in the built image, then your Docker build step isn’t actually producing it for the image you’re running. If it exists in the image but not in the running container, you’re almost certainly bind-mounting over /app.

Found the problem! It's an **adapter mismatch**.

**The Issue**

Your `package.json` uses `@sveltejs/adapter-static`:
```json
"@sveltejs/adapter-static": "^3.0.0"
```

But your start script expects a Node.js server:
```json
"start": "node build"
```

**`adapter-static`** generates static HTML/CSS/JS files — there's no `index.js` to run with Node.

**`adapter-node`** generates a Node.js server that can be started with `node build`.

**The Fix**

**Option A: Switch to `adapter-node`** (if you need SSR or a Node server)

```bash
npm uninstall @sveltejs/adapter-static
npm install @sveltejs/adapter-node
```

Then update your `svelte.config.js`:
```js
import adapter from '@sveltejs/adapter-node';
```

**Option B: Serve static files** (if you want a static site)

Change your Dockerfile's final stage to use nginx or a static server:

```dockerfile
# Production stage - serve static files
FROM nginx:alpine

COPY --from=builder /app/build /usr/share/nginx/html

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

And remove the `start` script dependency entirely.

---

**Which should you choose?**
- If your app uses SvelteKit's server-side features (form actions, server routes, SSR) → **Option A**
- If it's purely client-side (SPA) → **Option B** is simpler and more efficient
